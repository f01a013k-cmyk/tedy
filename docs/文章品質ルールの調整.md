# 文章品質ルールを自社の基準に合わせる

`src/jizokuka/knowledge/writing_rules.yaml` は、**審査で確実に減点される書き方**を
LLM を使わずに検出するためのルールです。公募要領に明記された規程ではなく、
審査実務からの経験則なので、回次に依存しません（`koubo_*.yaml` とは分離しています）。

支援機関ごとに「これは書かせない」という基準があるはずなので、調整してください。

## よくある調整

### 禁止する主観語を足す

```yaml
subjective_words:
  - words: [おまかせ, 職人技, 唯一]
    reason: 検証できない自己評価。工程・資格・実測値に置き換える
```

`reason` はそのままリライト指示に使われるため、
「どう直すか」まで書いてください。「使用禁止」だけでは LLM が直せません。

### セクションごとの数値要件を変える

```yaml
section_requirements:
  company_overview:
    min_numbers: 8        # 既定5。もっと数字を求めるなら上げる
    hints: [創業年, 従業員数, 売上推移, 商品点数, 客数, 商圏人口]
```

`hints` は不足時のリライト指示に「例: …」として差し込まれます。

### 業種特有の要件を足す

たとえば製造業で「歩留まり」を必ず書かせたい場合は、
`patterns` に検出パターンを足し、`section_requirements` から参照します。
`quality.py` の `check_section()` に対応する分岐を1つ加える必要があります。

## 調整したら必ずテストを回す

```bash
pytest tests/test_quality.py tests/test_samples.py
```

`tests/test_samples.py` は、同梱の模範解答と few-shot の「良い例」が
**ルールを全て通ること**を検証します。ルールを厳しくした結果ここが落ちるなら、
ルールが厳しすぎるか、例を書き直す必要があるということです。
プロンプトに「良い例」として見せる文章が自分の基準で不合格、という状態を防ぎます。

## severity の意味

| severity | 扱い |
|---|---|
| `must` | 残っている限りリライトが続き、`build` の終了コードが 1 になる |
| `should` | レポートに出るが、リライトの必須条件にはしない |

`must` を増やすとリライト回数（＝API費用）が増えます。
「本当に採択に響くか」で判断してください。
