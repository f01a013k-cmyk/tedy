# 小規模事業者持続化補助金 事業計画書

支援機関の工数の本体は、文章を書くことではなく **顧客への追加ヒアリングの往復** にある。
このスキルはそこを削ることを第一目的に設計されている。全部聞き返すのではなく、
業種知識で推論できることは推論で埋め、**推論を誤ると採択可否に響く項目だけ** を聞く。

## 手順

### 1. ヒアリングシートを読む

顧客からの入力は「創業50年」「自家製餡」「冷凍機」程度の単語の羅列であることを前提とする。
文章になっていないのが普通であり、それを責めない。`references/hearing_sheet.yaml` が雛形、
`references/hearing_sheet_example.yaml` が現場で実際に返ってくる粒度の例である。

まず売上推移・従業員数・創業年など、**そのまま事実として使える数字** を拾い出す。
「4200万」「約350万」のような表記も金額として解釈する。

### 2. ギャップ分析 — 推論で埋め、聞くことを絞る

`facts`（推論を含む確定事実）と `questions`（聞くべきこと）に切り分ける。

**推論で埋めるもの（質問しない）**
商圏人口、業種の一般的な原価率・客単価帯、競合が何社くらい存在するか、
どういう業態が競合になりうるか、市場の一般的な動向。
所在地・業種・売上規模から合理的に推定し、推定根拠を添えて `facts` に入れる。

**推論してはいけないもの（必ず質問する）**

| 項目 | 理由 |
|---|---|
| 競合他社の**社名** | 審査で「他社名を具体的に」と求められる。創作は事実誤認になる |
| 実在の取引先名・見積先名・見積金額 | 提出書類に載る固有名詞を作ってはならない |
| 購入する機器の型式と価格 | 経費明細と整合が取れなくなる |
| 決算の実数値（原価・販管費） | 決算書と食い違えば信用を失う |

**質問は最大8問まで。** 全部聞き返したら工数削減にならない。
採択可否に響かない項目（impact 4 未満）は推論で埋める。

### 3. 追加質問シートを出す

自由記述で聞くと返信が来ないか、来ても薄い。**必ず3〜5個の選択肢を添え、選ぶだけで済む形** にする。
選択肢はこちらの推定に基づく現実的な候補にする。各質問には「なぜ聞くか（どの審査観点に効くか）」を添える。
顧客は理由がわかると答えてくれる。

```markdown
## Q1. 冷凍機で最初に全国展開したい商品はどれですか
<sub>重要度 ★★★★★ / 確認理由: 補助事業計画の有効性（対象商品が定まらないと効果の積算ができない）</sub>

- [ ] どら焼き（主力・日持ちが短い）
- [ ] 季節生菓子（単価が高い・観光需要）
- [ ] 大福（リピート率が高い）
- [ ] その他（　　　　　　　　　　）
```

回答が来ない項目は、推定値で書いたうえで本文に `〈要確認: 推定根拠〉` を残す。
このマーカーが残っている限り機械検査がエラーを出して提出を止めるので、**捏造するより安全である**。

### 4. 下書きを書く（draft.yaml）

`draft.yaml` に全セクションを書く。形式は「draft.yaml の形式」節を参照。
執筆にあたっては「執筆の原則」と、各項目の分量・品質要件を守る。

セクションは順番に書き、前のセクションを踏まえて論理をつなぐ。
「1〜3の分析から導かれた方針である」と読めるようにするのが、
審査観点「経営方針・目標と今後のプランの適切性」の核心である。

各項目の見出し・分量・執筆指針は `references/koubo_r17.yaml` の `form_yoshiki2` にある。
書き方の水準を掴むには `references/section_examples.yaml`（項目ごとの悪い例／良い例）を読む。
完成形は `references/model_answer_yoshiki2.yaml`（様式2、本文9,887字）にある。

### 5. 機械検査を通す

```bash
python3 scripts/check_draft.py draft.yaml
```

主観語、数値の個数（年号は数えない）、算出式の有無、出典の有無、競合比較の密度、
月次スケジュール、年度別目標、分量不足、セクション間の重複、
そして公募要領の規程（補助率・上限額・対象外経費・経費区分・文字数・資金調達の整合）を検査する。

**要修正（must / error）がゼロになるまで直してから次に進む。**
指摘は「具体性を高める」ではなく「客単価と客数から算出式を書く」という粒度で出るので、
そのまま直せる。終了コードが 0 なら通過、1 なら未修正が残っている。

自分の文章を自分で採点すると甘くなる。この検査を飛ばさないこと。
実測で、自己採点85点「採択圏」の状態で出典なし・年度別目標なしが5件残っていた。

### 6. 様式に落とす

**支援機関の独自様式がある場合**（`assets/事業計画書_支援機関様式.docx` が同梱の例）

```bash
python3 scripts/fill_form.py fill.yaml -o 事業計画書_記入済.docx
```

相手の .docx をそのまま開いて記入欄と表だけを埋める。書式・見出し・罫線は様式側が保持される。
支援機関は自前の体裁で納品したいので、こちらの体裁で出し直すと使ってもらえない。
`fill.yaml` の書き方と、章番号が重複する様式への対応は
`references/model_answer_shien.yaml`（記入済みの実例、25項目・表5点）を参照。

**提出用の様式2・様式3**

```bash
python3 scripts/build_yoshiki.py draft.yaml -o ./out
```

様式2・様式3の .docx と経費明細の .xlsx が出る。Excel の補助金額は数式なので、
支援員が経費を直すと自動で再計算される。

### 7. 提出前の申し送りを添える

成果物と一緒に、次を支援員に伝える。

- `〈要確認〉` が残っている箇所と、誰に何を確認すべきか
- 相見積が必要な経費（税抜単価50万円以上）
- 公募要領ナレッジが未検証であること（後述）
- 推定で書いた数値と、その推定根拠

## 執筆の原則

**審査員は事業者を知らない。** 書かれていないことは存在しない。前提知識を要求する記述は書かない。

**数字のない主張は主張ではない。** 「売上が伸びる」ではなく
「客単価2,800円 × 新規客数月80人 × 12か月 = 年間268万円の増加」と書く。
算出に使う数値は入力データか、明示した推定根拠に基づくこと。

**捏造は絶対にしない。** 入力にない数値・固有名詞・出典を作らない。
推定が必要なら `〈要確認: …〉` を残し、根拠となる考え方を併記する。
この一貫性が支援員の信頼を守る。数値を作って点を取りに行くことは、支援機関の信用を賭けた行為になる。

**主観形容詞を使わない。** 「丁寧な」「こだわりの」「高品質な」「安心」は審査上ゼロ点。
検証可能な事実（工程・資格・年数・実測値・第三者評価）に置き換える。

**曖昧な数量表現を使わない。** 「多くの」「さまざまな」「大幅に」は数えていないことの表明である。
実数か割合で書く。

**記入欄を埋める。** 分量が目標の6割では「書くことがない事業」と映る。
ただし一般論や言い換えで字数を稼いではいけない。足りないときは
数値の内訳・根拠・具体例・前提条件を足して埋める。

**弱みと劣位を書く。** 強みだけ並べた分析は妥当性を疑われる。
弱みを挙げ、それをどう補うかまで書いて初めて分析として閉じる。

**一文は110字以内。** 審査員は短時間で読む。

文体は「である調」。箇条書きと地の文を混ぜ、審査員が3分で要点を掴めるようにする。

## draft.yaml の形式

```yaml
project_id: tanaka_seika
frame: 通常枠              # 通常枠 / 賃金引上げ枠 / 卒業枠 / 後継者支援枠 / 創業枠
specials: [インボイス特例]  # 上乗せ特例。無ければ []
company:
  name: 有限会社田中製菓
  representative: 田中太郎
  is_deficit: false        # 賃金引上げ枠の補助率に影響する

sections:                  # キーは koubo_r17.yaml の form_yoshiki2 と一致させる
  company_overview: |
    企業概要の本文…
  market_needs: |
  competition: |           # 競合他社との比較
  strengths: |
  policy_and_plan: |
  project_name: 冷凍生菓子のEC販売による全国贈答市場への販路開拓   # 30字以内
  sales_channel: |         # 最も分量を割く項目
  efficiency: |            # 任意記入だが書くと有利
  effect: |

expenses:
  - category: 機械装置等費          # koubo_r17.yaml の区分名に厳密に一致させる
    item: CAS機能付き特殊冷凍機 1台
    unit_price: 800000             # 税抜
    quantity: 1
    basis: ○○冷機 見積書（2026年3月10日付）による
    linked_activity: (1) 冷凍設備の導入   # 本文のどの取組に対応するか

funding:                   # 合計が補助対象経費と一致していること
  補助金: 900000
  自己資金: 450000
```

## 参照ファイル

必要になったときに読む。全部を先に読む必要はない。

| ファイル | 中身 | 読むとき |
|---|---|---|
| `references/koubo_r17.yaml` | 申請枠・補助率・上限額・経費区分・対象外経費・様式構成・分量・審査観点 | 金額や項目構成を確認するとき |
| `references/writing_rules.yaml` | 禁止する主観語、項目ごとの必要数値、検出パターン | 品質基準を確認するとき |
| `references/section_examples.yaml` | 項目ごとの「不採択になる書き方／採択レベルの書き方」の対 | 書き出す前。**これが最も効く** |
| `references/model_answer_yoshiki2.yaml` | 完成形（様式2、本文9,887字） | 分量と粒度の基準にするとき |
| `references/model_answer_shien.yaml` | 支援機関様式への記入済み実例（25項目・表5点） | 独自様式に流し込むとき |
| `references/hearing_sheet.yaml` | ヒアリングシートの雛形 | 顧客に渡すシートを作るとき |

模範解答の事業者・数値・統計・人名は**すべて架空**である。
書き方の型を真似るだけにして、数値や固有名詞を流用しない。
競合はA社・B社と匿名化してあるが、実際の申請では実名を書く。

## 必ず伝えること

同梱の `references/koubo_r17.yaml` は **未検証** である（`meta.verified: false`）。
補助上限額・補助率・経費区分・様式構成は回次ごとに変わる。

申請する回次の公募要領PDFと突合し、確認できたら `meta.verified` を `true` にする。
未検証のまま生成した場合は、成果物を渡すときに必ずその旨を伝える。
金額を間違えた計画書は、文章がどれだけ良くても意味がない。

このスキルは申請書作成を支援するものであり、**採択を保証するものではない**。
生成物は支援員が内容を確認し、事業者本人の意思と事実に基づく記述であることを
確かめたうえで提出する。
