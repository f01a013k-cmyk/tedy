# jizokuka — 小規模事業者持続化補助金 事業計画書 自動作成システム

単語レベルしか埋まっていないヒアリングシートから、公募要領に準拠した
**採択レベルの事業計画書（様式2・様式3）**を生成します。

支援機関の最大の工数は「文章を書くこと」ではなく **「顧客への追加ヒアリングの往復」** です。
本システムはそこを削ることを第一目的に設計されています。

---

## 何が自動化されるか

| 従来の工数 | 本システム |
|---|---|
| 単語しかないシートを見て、何を聞くべきか考える | **ギャップ分析**が推論で埋め、聞くべき数問だけ抽出 |
| 顧客に自由記述で質問 → 返信が来ない／薄い | **選択肢付き質問シート**を自動生成（選ぶだけ） |
| 白紙から本文を書く | 審査観点に紐づけて**セクション別に執筆** |
| 自分では良し悪しが判断できない | **審査員視点で自己採点 → 弱点だけリライト** |
| 公募要領を読み返して金額・文字数を検算 | **決定論的な準拠チェック**（LLM任せにしない） |
| 「これで通るのか」が分からない | **文章品質の機械検査**で減点要因を確定 |
| 書いても記入欄が埋まらない | 下限・目標・上限の**3段管理**で分量を担保 |
| 様式へ転記 | Word / Excel / Markdown を**同時出力** |

---

## まず何が出るか見る（APIキー不要）

```bash
jizokuka sample -o ./sample_outputs
```

同梱の模範解答（架空事例）から、様式2・様式3の Word、経費明細の Excel、
スコアレポートを実際に生成します。LLM を呼ばないので課金されません。
**「採択レベルとはどの粒度か」の基準**としても使えます。

## 使い方

```bash
# 1. ヒアリングシートの雛形を出す（顧客に記入してもらう。単語でOK）
jizokuka template hearing.yaml

# 2. 案件として取り込む（yaml / json / csv / xlsx に対応）
jizokuka new tanaka --from hearing.yaml

# 3. ★ここが本命★ ギャップ分析 → 追加質問シートを生成
jizokuka ask tanaka
#    → projects/tanaka/outputs/追加質問シート.md を顧客に送付
#    → 回答を projects/tanaka/answers.yaml に転記

# 4. 生成（執筆 → 採点 → リライト → 準拠チェック）
jizokuka build tanaka

# 5. 手直し後の再チェック
jizokuka check tanaka
```

### 成果物

`projects/<案件ID>/outputs/` に出力されます。

| ファイル | 用途 |
|---|---|
| `様式2_経営計画書兼補助事業計画書1.docx` | 提出用 |
| `様式3_補助事業計画書2.docx` | 提出用（経費明細表・資金調達方法） |
| `経費明細・資金調達.xlsx` | 金額調整用。**補助金額は数式**なので経費を直すと自動再計算 |
| `事業計画書.md` | レビュー・差分管理用 |
| `審査スコアレポート.md` | 内部資料。観点別スコアと改善指示、要確認箇所の一覧 |
| `追加質問シート.md` | 顧客送付用 |

`jizokuka build` は、公募要領の準拠エラーか `must` 級の品質指摘が残っている場合、
終了コード 1 を返します。CI やバッチ処理で提出可否を判定できます。

公式の様式 .docx が手元にある場合は、`{{company_overview}}` のような
プレースホルダを置いておけば書式を保ったまま流し込めます。

```bash
jizokuka render tanaka --template 様式2.docx
```

## 設計上の重要な判断

### 1. 質問を減らすことが最大の価値

`gap analyze` は業種知識から推論できることを `facts` として埋め、
**推論を誤ると採択可否に響く項目だけ**を質問にします（既定で最大8問）。
質問には必ず選択肢が付き、顧客は選ぶだけで済みます。

推定値には `confidence: inferred` と推定根拠が残るため、
支援員は「どこが推測か」を後から追えます。

### 2. 捏造させない

LLM は数値を作るのが得意で、それが補助金申請では致命傷になります。
本システムは入力に無い数値を書く代わりに `〈要確認: …〉` マーカーを残させ、
**マーカーが残っている限り準拠チェックが `error` を出して提出を止めます。**
Word 出力にも赤字で警告が入ります。

### 3. LLM の自己採点だけを信じない

LLM に自分の文章を採点させると甘くなります。そこで `pipeline/quality.py` が
**LLM を通さずに**、審査で確実に減点される書き方を検出します。

- 主観形容詞（丁寧・こだわり・高品質）の使用
- セクションごとの数値の個数不足（年号は数えない）
- 効果の算出式（単価×客数×期間）の欠落
- 市場動向の出典なし／実施スケジュールが月次でない／年度別目標がない
- 具体策を伴わないバズワード、曖昧な数量表現、110字超の一文
- セクション間の記述の重複

これらは `must`（必ず直す）と `should`（直すと良い）に分かれ、
**`must` が残っている限り、自己採点が何点でもリライトが続きます。**
指摘は「具体性を高める」ではなく「客単価と客数から算出式を書く」という
粒度なので、そのままリライト指示として使えます。

同じ要件は執筆プロンプトにも渡すため、初回ドラフトの時点で満たされやすく、
結果としてリライト回数＝API費用が減ります。

### 4. 分量は下限・目標・上限の3段で管理する

LLM は放っておくと短くまとめます。実測では記入欄の約60%しか埋まりませんでした。
記入欄が埋まっていない計画書は、審査員に「書くことがない事業」と映ります。

そこで `koubo_*.yaml` の各項目に `min_chars` / `target_chars` / `max_chars` を持たせ、

- 執筆プロンプトでは **target を使い切れ** と指示する
- `min_chars` を割ると品質チェックが `must` を出し、加筆されるまでリライトが続く
- 字数稼ぎの一般論を禁じ、数値の内訳・根拠・具体例・前提条件で埋めさせる

同梱の模範解答は本文9,887字（様式2全体）で、各欄の充足率は87〜101%です。
**few-shot の分量が生成文の分量を決める**ため、模範解答自体が目標分量を
満たしていることをテストで保証しています。

分量の目安は回次や支援機関の方針で変わるので、YAML で調整してください。

### 5. 競合分析は推論させず、必ず聞く

審査観点「経営状況分析の妥当性」で最も差がつくのが競合分析です。
様式2には独立した項目「2-3 競合他社との比較」を設けています
（公式様式2の採番1〜4を崩さないよう 2-3 に置いています）。

- **競合の社名は推論禁止**。入力に無ければ `impact 5` の質問として必ず聞きます。
  社名の創作は事実誤認になるためです
- 自社と競合を並べた記述が3箇所未満なら要修正
- **優位だけでなく劣位も書かせます。** 劣位を隠すと分析の妥当性を疑われるため、
  劣位をどう補うかまで書いて初めて分析として閉じます

ヒアリングシートの `competitors` 欄は、顧客に必ず記入してもらってください。
店名だけでも構いません。ここだけは業種知識で埋められません。

### 6. 抽象的な指示ではなく、良例と悪例を見せる

`knowledge/section_examples.yaml` に、セクションごとの
「不採択になる書き方」と「採択レベルの書き方」を対で持たせ、
執筆時にそのセクションの分だけプロンプトに注入します。
`examples/` 全体を毎回入れるとトークンを浪費し、無関係な例に引きずられるためです。

完成形は `src/jizokuka/examples/tanaka_seika_模範解答.yaml` にあります。
これは `jizokuka sample` で成果物として出力でき、テストでは
**模範解答自身が品質チェックと準拠チェックを全て通ること**を検証しています
（自分の基準を満たさない例を few-shot に使うわけにいかないため）。

### 7. 規程の適合判定は LLM にさせない

金額・補助率・上限額・文字数・対象外経費は `pipeline/compliance.py` が
**コードで検証**します。補助率は `Fraction` で扱うため、
`600,000 × 2/3 = 400,020` のような丸め事故が起きません。

### 8. 公募要領は外部ファイル

回次ごとに金額も様式も変わります。
`src/jizokuka/knowledge/koubo_r17.yaml` を差し替えるだけで新回次に対応できます。

```bash
jizokuka koubo --verify     # 公募要領PDFとの突合チェックリストを出力
```

> **⚠️ 同梱の `koubo_r17.yaml` は `verified: false` です。**
> 金額・補助率・様式構成は雛形であり、**申請する回次の公募要領PDFと必ず突合してください。**
> 未検証のまま生成すると、全成果物に警告が付きます。

## 開発

```bash
pytest                      # 104件。LLM はスタブ化されるので API キー不要
jizokuka build tanaka --dry-run    # LLM を呼ばずに配線だけ確認
```

LLM 応答は `.jizokuka_cache/` にキャッシュされます（`--no-cache` で無効化）。

### 構成

```
src/jizokuka/
├── knowledge/
│   ├── koubo_*.yaml         公募要領ナレッジ（回次ごと・要検証）
│   ├── writing_rules.yaml   文章品質ルール（回次非依存の経験則）
│   └── section_examples.yaml セクション別 few-shot（良例/悪例）
├── examples/                サンプルヒアリングシートと模範解答
├── knowledge.py             ナレッジのロードと静的検証
├── models.py                データモデル（単語レベル入力を許容）
├── llm/prompts/*.md         プロンプト（システムの頭脳）
├── templates/               ヒアリングシート雛形
├── pipeline/
│   ├── ingest.py            yaml/json/csv/xlsx 取込
│   ├── gap.py               ギャップ分析・追加質問生成
│   ├── expense.py           経費の構造化と積算根拠
│   ├── draft.py             セクション別執筆
│   ├── quality.py           文章品質の機械検査（LLM 不要）
│   ├── review.py            審査観点による採点
│   ├── revise.py            弱点セクションのリライト
│   └── compliance.py        公募要領準拠チェック（決定論的）
├── render/                  Word / Excel / Markdown 出力
├── samples.py               模範解答の読み込み
├── generator.py             パイプラインのオーケストレーション
└── cli.py                   CLI
```
